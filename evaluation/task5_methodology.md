# Задача 5. Метод интеллектуального поиска по карточкам товаров

Документ для пояснительной записки: постановка задачи, состав метода, параметры и реализация в проекте.

## 1. Постановка

Требуется обеспечить поиск по каталогу карточек товаров так, чтобы запросы в свободной форме (в том числе с перефразом и смешением языков) давали релевантную выдачу, сочетая **семантическое** сопоставление на основе **языковой модели эмбеддингов** и **лексическое** сопоставление по тексту карточки.

## 2. Представление документа (карточки)

Для каждого оффера формируется агрегированный текстовый **пассаж** (функция `build_offer_text` в `search_index.py`):

- краткое наименование;
- производитель;
- категория;
- пары «название характеристики: значение» и одиночные значения.

Пассаж индексируется в двух каналах:

1. **Векторный канал** — эмбеддинг пассажа (см. §3).
2. **Лексический канал** — полнотекстовый индекс PostgreSQL (`tsvector` по полю `search_text`, конфигурация `russian`).

## 3. Языковая модель и семантический поиск

Используется модель **sentence-transformers** `intfloat/multilingual-e5-small` (размерность 384). Для семейства E5 применяются:

- префикс запроса: `query: {текст запроса}`;
- префикс документа: `passage: {текст пассажа}`;
- нормализация векторов (`normalize_embeddings=True`), поиск по **внутреннему произведению** (эквивалент косинусной близости для нормированных векторов).

**Хранение и поиск:**

- основной быстрый путь — **FAISS** `IndexFlatIP` и файлы в каталоге `search_artifacts` (или путь из `SEARCH_INDEX_DIR`);
- при отсутствии FAISS-артефактов возможен fallback на колонку **pgvector** `embedding_vec` (если расширение и колонка настроены в БД).

На этапе ранжирования для маршрута `/search` из каждого канала берётся до **200** кандидатов с рангами.

## 4. Лексический поиск

Запрос обрабатывается через `websearch_to_tsquery('russian', q)`; ранжирование — `ts_rank_cd` по совпадению с `tsvector` пассажа. Возвращается упорядоченный список офферов (до **200** позиций с рангами).

## 5. Гибридное слияние (RRF)

Списки кандидатов из семантического и текстового каналов объединяются методом **Reciprocal Rank Fusion**:

\[
\text{score}(d) = \sum_{c \in \{\text{semantic}, \text{text}\}} \frac{1}{k + r_c(d)}
\]

где \(r_c(d)\) — ранг документа \(d\) в канале \(c\) (если документа нет в списке канала, вклад 0). В реализации: **k = 60**, после сортировки по убыванию score сохраняется до **500** идентификаторов (`rrf_merge` в `search_index.py`, вызов из `main.py`).

## 6. Постфильтрация по токенам запроса

Чтобы снизить долю «семантически близких, но не по смыслу запроса» ответов, к упорядоченному списку применяется **постфильтр** (`filter_offer_ids_by_query_tokens`):

- из запроса извлекаются значимые токены (слова и числа, без стоп-слов и короткого шума);
- оффер остаётся в выдаче только если **каждый** токен находится в агрегированном тексте карточки (с учётом отдельных чисел и упрощённого сопоставления через «сжатие» пробелов/дефисов для моделей вроде `GF-63` vs `GF63`).

Если после токенизации не осталось токенов, фильтр не меняет порядок.

## 7. Пользовательский сценарий и администрирование

- Поиск на витрине: **GET** `/search?q=…` (пагинация как у каталога).
- Построение индекса после обновления каталога: админка **«Нормализация каталога»** → «Собрать поисковый индекс» (**POST** `/admin/search-index/build`).
